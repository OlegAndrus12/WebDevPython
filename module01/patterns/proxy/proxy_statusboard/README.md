
| [`app.py`](app.py) | копія застосунку з [`../../04_uv/`](../../04_uv/); маршрути незмінні, унизу файлу додано підключення проксі |

## Що це таке

**Proxy** — структурний патерн: об'єкт з тим самим інтерфейсом, що й річ, яку
він приховує, і який стоїть між викликачем і цією річчю. Виклик виглядає так
само, як прямий, але проксі може відповісти сам, змінити запит чи відповідь,
або не пропустити виклик далі взагалі.

GoF виділяє чотири різновиди — protection, caching, virtual, remote, а ще
smart reference. Тут навмисно взято лише один, у чистому вигляді:

| Різновид | Що робить | Middleware тут |
| --- | --- | --- |
| **Protection** | вирішує, пропускати виклик, чи ні | `block_ip_middleware` |

Решта — caching, smart reference — це той самий фолд
`(environ, start_response) -> app(...)`, лише з іншим тілом.
[`../03_proxy_middleware.py`](../03_proxy_middleware.py) показує всі чотири
одразу на іграшковому прикладі; тут — один, доведений до реального
застосунку, щоб не розмивати увагу.

## Той самий middleware, дві мови

[`../../patterns/middleware.py`](../../patterns/middleware.py) — старий файл
із цього ж репозиторію, `BlockIPMiddleware` для Django:

```python
class BlockIPMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        ip = self.get_client_ip(request)
        if ip in BLOCKED_IPS:
            return HttpResponseForbidden("Your IP is blocked.")
        return self.get_response(request)
```

Клас там — не бізнес-вимога, а форма, якої вимагає протокол Django:
middleware реєструють об'єктом, тому й потрібні `__init__`/`__call__`. WSGI
вимагає лише один викликаний об'єкт, тому [`middleware.py`](middleware.py)
робить те саме замиканням, без класу:

```python
def block_ip_middleware(app):
    def wrapped(environ, start_response):
        if _client_ip(environ) in _BLOCKED_IPS:
            ...
        return app(environ, start_response)
    return wrapped
```

`_client_ip()` повторює ту саму логіку, що й `get_client_ip` у Django-файлі:
спершу `X-Forwarded-For` (перший IP у списку, якщо запит пройшов через кілька
проксі), і лише якщо його немає — `REMOTE_ADDR`. Без цього порядку застосунок
за реверс-проксі бачив би в `REMOTE_ADDR` адресу самого проксі, а не
відвідувача, і блокування не спрацювало б узагалі.

Підключається middleware унизу [`app.py`](app.py), одразу після останнього
маршруту:

```python
app.wsgi_app = block_ip_middleware(app.wsgi_app)
```

## Що показує `block_ip_middleware`

**Жоден маршрут у `app.py` не має рядка коду про блокування.** `board`,
`incidents_page`, `add_service`, `delete_service` лишаються про те, про що й
мали бути. Перевірка "чи можна цій адресі бачити застосунок узагалі" — один
рядок унизу файлу, а не перед кожним `return`.

Заблокована адреса не потрапляє до Flask взагалі — `wrapped()` повертає 403
сам, `app(environ, start_response)` навіть не викликається. Це і є "protection
proxy": на відміну від кешу (`Caching`, який завжди відповідає чимось), цей
різновид може відповісти "ні" й ніде більше про запит не почути.

## Спробувати самому

Поки сервер запущено (`uv run python ../08_patterns/proxy/run.py` з
`04_uv/`), у другому терміналі:

```bash
curl -i http://127.0.0.1:5001/                                       # 200 — REMOTE_ADDR не в списку
curl -i -H "X-Forwarded-For: 192.168.1.10" http://127.0.0.1:5001/    # 403 — заблокована адреса
curl -i -H "X-Forwarded-For: 203.0.113.7" http://127.0.0.1:5001/     # 200 — інша адреса, пройшло
curl -i -H "X-Forwarded-For: 10.0.0.1, 203.0.113.7" http://127.0.0.1:5001/  # 403 — читає першу адресу в списку
```

## Чому копія, а не `sys.path`

`app.py`, `services.py`, `checks.py`, `incidents.py`, шаблони й статика в цій
теці — копія з [`../../04_uv/`](../../04_uv/), а не імпорт через `sys.path` у
сусідню теку. `04_uv` не запакований (немає `[build-system]`, плаский
`import services` — див. CLAUDE.md репозиторію), тому "правильного" імпорту
звідти й не існує; тягнути його теку в `sys.path` означало б, що приклад
патерна тихо залежить від того, що лежить за межами його власної папки.
Копія самодостатня і не ризикує зачепити `04_uv`, поки той викладається
окремо як приклад для іншої теми (uv).

Саме тому middleware підключено прямо в цій копії `app.py`, а не в
оригіналі: правило, яке в описі патерна виглядає гарно ("не змінюй теку
іншого заняття"), і рішення, яке з нього випливає ("зроби копію і зміни її"),
— різні речі, і тут видно обидві.

## А що з іншими різновидами проксі

Усі є в цьому ж репозиторії, просто не написані руками:

- **Caching і virtual proxy** (відповідає з пам'яті / відкладає дороге
  створення) — обидва це `@lru_cache` з [`../singleton/`](../singleton/README.md):
  об'єкт `Settings` не існує, поки його не запросили вперше, а другий запит
  отримує вже готовий.
- **Remote proxy** (ховає мережу за локальним інтерфейсом) — сам
  `requests.get(url)` у [`checks.py`](checks.py): виклик виглядає як
  звернення до локального об'єкта, а насправді йде HTTP-запит.
- **Smart reference** (завжди пропускає, додає поведінку навколо) —
  логування чи метрики на тому самому рівні WSGI.

Повний набір усіх чотирьох на іграшкових об'єктах — в
[`../03_proxy_middleware.py`](../03_proxy_middleware.py). Писати кожен
окремим класом у Python рідко має сенс — це саме той пункт, який той файл
називає ціною патерна: "control flow стає невидимим у місці виклику", і
платити за це варто лише тоді, коли дійсно потрібно підмінити виклик, а не
тому, що підручник каже "Proxy — це клас з таким самим інтерфейсом".

## Підсумок

Проксі — це "той самий інтерфейс, інша поведінка навколо виклику". У Python
на рівні HTTP цей інтерфейс уже є готовий і стандартизований — WSGI (і його
наступник ASGI), тому власний клас-проксі рідко пишуть з нуля: обгортають
`wsgi_app`, як тут, або йдуть готовим middleware з фреймворку. Django просить
для цього клас; WSGI — лише функцію. Патерн вартий уваги не заради коду, який
його реалізує, а заради питання, яке він змушує поставити: **де саме в стеку
має жити ця перевірка** — усередині обробника чи навколо нього.
