Software Testing

Unit · Integration · End‑to‑End · Load

Four kinds of test that sound like four sizes of the same thing. They are not. Three of them ask is it correct? and differ only in how much of the system is real. The fourth asks a different question entirely.

Unit

One piece, alone. Everything it touches is faked.

Integration

Several pieces wired together. The seams are real.

End-to-end

The whole system, the way a user meets it. Nothing faked.

Load

The whole system, many users at once. Output is a number, not a verdict.

The distinction that matters

Each level asks a different question

If you remember one thing: the level is chosen by the question, not by the size of the code under test.

Unit

“Is this piece of logic right?”

Does hash_password salt? Does the discount round half-up? Pure logic, called directly, with no database, no clock, no network. Milliseconds. Hundreds of them.

Integration

“Do these pieces agree with each other?”

Does the route actually call the service? Does the ORM write the column the query reads back? Does the JSON shape match the schema? The seams are what is under test.

End-to-end

“Can a real user actually do this?”

Register → click the link in the email → log in → like an article → see it in the list. Real browser, real HTTP, real database, real mail. Slow, fragile, and the only test that would have caught the typo in your JavaScript.

Load

“Does it still work when 500 people do it at once?”

Not does it work — it already passed the other three. Under concurrency: how slow, at what point, and what breaks first. The answer is a latency curve, not a green checkmark.

Load testing is the odd one out. Unit, integration and E2E are the same axis at three zoom levels — each one makes more of the system real. Load testing is a different axis: the system is fully real, and what varies is the number of users.

Unit

One piece, in isolation

The function is called directly. Nothing else in the system is running.

# tests/test_security.py — no database, no HTTP
async def test_hashing_is_salted():
    first  = await auth_service.hash_password("hunter2")
    second = await auth_service.hash_password("hunter2")

    assert first != second
    assert await auth_service.verify_password("hunter2", first)
Runs in~2 ms, no setup at all
Catcheswrong algorithms, bad edge cases, off-by-one, regressions in pure logic
Misseseverything about how pieces connect — a perfectly-tested function wired to nothing still passes
Fails whenyou change behaviour or merely refactor — this is the cost of testing internals
Integration

Several pieces, wired together — the seams are the subject

The app runs in-process. The router, the dependency injection, the ORM and a real SQL engine all participate; the slow outside world does not.

# tests/test_articles_api.py — real routing, real SQL
async def test_listing_returns_newest_first(client, auth_headers, articles):
    made = await articles.create_many(3)

    response = await client.get("/api/articles", headers=auth_headers)

    assert response.status_code == 200
    assert [a["id"] for a in response.json()["articles"]] == [a.id for a in made]
Runs in~30 ms each; the whole suite in ~3 s, no Docker
Catcheswrong status codes, missing auth on a route, ORM/schema mismatch, broken ordering, N+1 queries
Missesanything above HTTP (your JS), and anything the fakes paper over — SQLite is not Postgres
Best valuethe highest confidence-per-second in the whole suite; most of your tests belong here
End-to-end

The whole system, exactly as a user meets it

A real browser drives a running stack. Nothing is substituted — the app really sends mail, and the test reads the link back out of the inbox.

# tests/e2e/ — a real Chrome against the compose stack
fill(driver, "email", email)
fill(driver, "password", PASSWORD)
driver.find_element(By.ID, "register-btn").click()

link = verification_link(email)   # read from Mailpit
driver.get(link)
...
assert driver.execute_script("return localStorage.cnn_token")
Runs in~8 s for one flow — and needs the whole stack up first
Catchesthe bugs nothing else can: a token stored under the wrong localStorage key, a fetch missing its Authorization header, a template rendering the wrong data-article-id
Costsslow, flaky (timing, waits, animations), and when it fails it tells you “the flow is broken” — not where
Rulewrite few, and only for journeys that make money — sign-up, checkout, login
Load

Same system, many users — and the output is a measurement

Nothing here is about correctness. The code already works for one user. The question is what happens at fifty, at five hundred, and which resource gives out first.

# tests/load/locustfile.py
class Reader(HttpUser):
    wait_time = between(1, 3)

    @task
    def list_articles(self):
        self.client.get("/api/articles", headers=self.headers)

# locust --headless -u 50 -r 10 -t 30s
Askshow does latency change as concurrency rises, and what breaks first
Catchesconnection-pool exhaustion, N+1 queries that were invisible at one user, missing indexes, memory growth, lock contention
Needsa production-like environment — a load test against SQLite on a laptop measures your laptop
Readp95, not the average. The mean hides the slow tail that your users actually notice

Related shapes: stress (raise load until it breaks, to find the ceiling) · soak (normal load for hours, to find leaks) · spike (0→2000 in seconds, to test elasticity).

The trade is always the same one: speed and precise blame on one end, realism and true confidence on the other. You cannot buy both, so you buy some of each.

Proportions

How many of each — and why load sits off to the side

Why the shape

Cost per test rises by roughly 10× at each level, and so does the time to diagnose a failure. A broad base means most bugs are caught by the cheapest test that can catch them.

The two failure shapes

Ice-cream cone (mostly E2E): a suite that takes 40 minutes, fails randomly, and that everybody re-runs instead of reading.
Hourglass (no middle): thousands of green unit tests and a product where nothing fits together.

The honest modern version

Many teams now push the middle layer widest — the “testing trophy”. Integration tests exercise real seams at near-unit speed, which is where most real bugs actually are. Treat the pyramid as a hint about cost, not a quota.

In practice

A warning about vocabulary

“Integration test” means five different things

These names are not standardised. In an interview, or a new team, ask what they mean before you agree.

What people call “integration”

  • two classes together, database still faked
  • the app in-process against a real database ← this deck's usage
  • an HTTP call to a service running in a container
  • our service against another team's service
  • anything that isn't a unit test

What people call “unit”

  • one function, everything mocked (classic / “London”)
  • one behaviour, using real collaborators (“Chicago”)
  • anything that runs fast and needs no setup ← the practical definition

The argument over where “unit” ends is decades old and has never been settled. It doesn't need to be.

Better questions than “what level is this?”
  • What is real in this test, and what is faked?
  • How long does it take, and what setup does it need?
  • When it goes red, will I know where to look?
  • Would it have caught the last bug we shipped?
Answer those four and the label stops mattering.

Takeaways

Six things worth keeping

1 · The axis is realism, not size

Unit → integration → E2E is one dial: how much of the system actually runs. Every fake you remove buys truth and costs seconds.

2 · Load asks a different question

The other three ask “is it correct”. Load asks “is it still correct fast enough, at N users”. Its output is a measurement, so it needs a baseline to be meaningful.

3 · The middle layer is underrated

Most real bugs live in the seams between components — and integration tests hit those seams at nearly unit-test speed.

4 · Write few E2E tests, and mean them

They catch what nothing else can, and they are the tests that people learn to ignore. Reserve them for the journeys you cannot afford to break.

5 · Catch it at the cheapest level that can

When an E2E test finds a bug a unit test could have found, that is a signal — write the cheap test too, so next time it fails in two seconds instead of two minutes.

6 · Coverage is not confidence

100% line coverage with everything mocked proves the code runs. It doesn't prove the pieces fit, the browser works, or the thing survives Monday morning.
